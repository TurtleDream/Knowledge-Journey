
# skills.md — правила работы с этим репозиторием

Этот файл — инструкция для ИИ-ассистента, помогающего с разработкой
Knowledge Journey. Цель — чтобы код, комментарии, коммиты и документация
выглядели как работа одного разработчика, а не как сгенерированный текст.

Читай этот файл ПЕРЕД тем, как предлагать код, писать коммиты или
документацию. Если правило противоречит твоим дефолтным настройкам —
следуй правилу из этого файла.

---

## 1. Общие принципы

1. **Никакой "AI-полировки".** Не используй характерные обороты: 
   "давайте рассмотрим", "важно отметить", "в заключение", "стоит 
   подчеркнуть", "это позволяет нам", "таким образом", "более того".
2. **Не объясняй очевидное.** Комментарий `// получаем пользователя` 
   над `getUser()` — мусор. Комментарий должен объяснять **почему**, 
   а не **что**.
3. **Не пиши "идеальный" код.** Реальный код имеет допущения, TODO, 
   закомментированные альтернативы, "пока так". Это нормально.
4. **Не бойся несовершенства.** Если решение работает и понятно — 
   не рефактори его до "best practices" без причины.
5. **Короткие имена.** `userCtx`, `idx`, `tmp`, `res` — нормально, 
   если область видимости маленькая. Не пиши 
   `currentUserPersonalizationContextService` — это маркер ИИ.

## 2. Стиль комментариев (TypeScript)

**Плохо (ИИ-стиль):**
```typescript
// This function initializes the SQLite database connection
// and sets up the necessary tables for storing user data.
// It also handles the persistence layer using IndexedDB.
async init(): Promise<void> {
```

**Хорошо (человеческий стиль):**
```typescript
// Поднимаем sql.js. WASM лежит в assets — если путь поменялся, 
// тут же поправить locateFile.
async init(): Promise<void> {
```

**Правила:**
- Русский язык для комментариев (проект русскоязычный)
- Комментарии — только там, где есть неочевидное решение или подводный камень
- Не комментируй сигнатуры функций — TypeScript сам справится
- TODO пиши честно: `// TODO: разобраться почему embedBatch падает на 51+ элемента` — не `// TODO: improve error handling`
- Если код временный — помечай `// FIXME` или `// временно, потом ...`
- Никаких "Note:", "Important:", "Caution:" — это маркеры ИИ

## 3. Именование

**Переменные:** camelCase, короткие. `topicMastery`, `lastMistakes`, `topK`.

**Функции:** глагол + объект. `chunkArticle`, `embedBatch`, `markStudied`. 
Не `processArticleChunking`, не `handleEmbeddingOperation`.

**Классы/сервисы:** PascalCase + суффикс по роли. `SqliteService`, 
`RagService`, `ContentChunkerService`. Суффикс `Service` — норма в Angular, 
не избегай.

**Константы:** SCREAMING_SNAKE только для реальных констант 
(`MAX_CHUNKS_PER_BATCH`, `EMBEDDING_MODEL`). Не превращай всё в константы 
без причины.

**Типы/интерфейсы:** без префикса `I`. `Chunk`, `Source`, `TopicMastery`. 
Не `IChunk`, не `ChunkInterface`.

## 4. Структура файлов

- Один сервис — один файл.
- Файлы не больше 300 строк. Если больше — режь.
- Импорты сортируй: сначала angular, потом внешние, потом свои. 
  Между группами — пустая строка.
- Экспортируй только то, что нужно. Не делай `export` на всё подряд.
